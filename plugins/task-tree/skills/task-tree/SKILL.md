# Task Tree:递归任务分解方法论

一套把"大任务"组织成递归目录树的方法:每个任务对应一个目录,目录下唯一一份
`00-实施计划.md` 记录背景/目标/计划/状态跟踪图,是这个任务的**唯一真相**;执行
过程中产出的原始数据/日志/脚本放进 `99-产物桶`,只是**证据**——证据丢了,只要
任务结构(所有 `00-实施计划.md`)还在,任务蓝图依然完整。

## 核心模型

一个任务 1:1 关联一份实施计划;实施计划由多个步骤组成;步骤(及其依赖、状态)
画出来就是状态跟踪图。**状态跟踪图不是独立于计划的另一样东西,是步骤的可视化
呈现。**

## 目录规则

整棵树只存在两种目录,不允许第三种:

1. **任务目录**:内部有 `00-实施计划.md`
2. **`99-产物桶`**:固定名字,唯一允许的第二种

这两种目录的**父目录必须是任务目录**;根目录本身必须是任务目录。

`99-产物桶` 内部是自由区,**不受"必须是任务型目录"这条约束**——原始脚本、
日志、原始调用记录这类东西可以直接以普通文件夹存放(比如 `证据包/`、
`实测与实验/`、`设计文档/`),不需要它们也有自己的 `00-实施计划.md`。

一个任务目录下只允许**一个文件**:`00-实施计划.md`。任务执行过程中产出的一切
其他内容,必须放进子文件夹(子任务目录或 `99-产物桶`),不能作为游离文件散落
在任务目录里。

## 编号约定

| 编号 | 含义 | 类型 |
|---|---|---|
| `00` | `00-实施计划.md` | 文件,任务目录下唯一的文件 |
| `01`–`89` | 子任务目录,按开出顺序递增分配 | 目录 |
| `99` | `99-产物桶` | 目录,固定名字,每个任务目录至多一个 |

`00` 前缀的作用是在脚本/`git`/终端场景下保证排序第一(这些场景不区分文件/
文件夹类型,纯按字符排序)。**在 VS Code 等"文件夹优先于文件"排序的浏览器里,
`00-实施计划.md` 会显示在所有子文件夹之后**——这是可接受的权衡,不要试图用
命名技巧对抗它:找到这个入口文件靠的是"一个任务目录只有一个文件"这条**唯一性**
规则,不靠它排第几。`99` 用最大数字是因为它在文件夹里天然排最后,恰好紧邻其后
唯一的文件 `00-实施计划.md`,两者在视觉上会聚在一起。

## 什么时候该把一个步骤扇出成子任务

默认不拆——一个任务的所有步骤先老老实实待在同一份 `00-实施计划.md` 里当步骤
记录,只有满足以下任一条件才考虑升级成独立子任务目录:

- **横向扇出过宽**:同一层级的步骤/候选数超过 **5**(状态图里的判定节点/"闸"
  不计入这个计数,它们是瞬时判断不是工作项)。**宽扇出优先尝试用表格折叠**
  (在同一份实施计划里用表格列出多条,而不是逐条展开成小节),表格折叠不住
  (比如每条都需要自己的过程记录、需要跨会话跟进)才升级成文件夹。
- **纵向深度信号**:这个步骤本身会跨多次会话持续推进、需要自己独立的证据
  链/审计轨迹、或者会被其他任务引用,即便它在扇出计数上并不"宽"。

**这个判断是持续性的,不是任务一开始时就要设计出整棵树**——先扁平记录,
长出规模了再拆分,不要提前设计好一整棵树的结构。

**同一层级允许"已升级为子任务的节点"和"仍是普通步骤的节点"混合共存**,不要求
整齐划一(不能因为兄弟节点里有一个升级了,就强迫其余简单步骤也跟着开文件夹,
那会导致给根本不需要独立追溯的步骤编造背景/目标)。在状态跟踪图里,给已升级
的节点用专门的样式(比如单独的 `classDef`)做视觉区分,让读者一眼看出"这个
节点点进去还有故事,那个节点讲完了就是讲完了"。

## 扇出操作步骤

决定要把某个步骤升级成子任务时,按以下顺序动手:

1. 从当前(父)任务的实施计划里,识别出该独立成子任务的那部分步骤
2. 建一个新的子任务目录,编号取该父任务目录下 `01`–`89` 里下一个可用的号
3. 在子任务目录里建 `00-实施计划.md`
4. 把相关步骤从父任务实施计划里**取出来**,放进子任务实施计划——**不是原样
   粘贴**:子任务的 `00-实施计划.md` 必须补写背景(为什么会有这个任务)和目标
   (要回答什么问题),不能只有一份裸步骤列表。这是因为每个任务的实施计划都要
   满足"背景+目标+计划+状态跟踪图"这个基本结构,光有步骤不满足。
5. 用这些步骤在子任务实施计划里生成它自己的状态跟踪图
6. 回到父任务的状态跟踪图,把原来那几个步骤对应的节点**收拢成一个节点**
   ("见子任务 XX"),不再展示细节。这个节点的状态由下面的级联更新机制驱动,
   不是手动同步。

## 横切任务

一个任务如果内容上适用于/横跨多个兄弟任务,它的归属**按内容判断,不按提出
者**——即便它是被某个具体任务的工作过程中发现/提出的,只要它的内容主题实际上
横跨多条线,就应该在状态跟踪图里**独立成一个节点**,用**虚线**连接到它横跨
的每一个任务(表示"作用于"关系),而不是画成某一个任务的子节点(实线父子
关系)。虚线和实线在同一张图里要能一眼区分开。

## 级联更新

父节点的 `00-实施计划.md` 里必须有**唯一一张**子节点状态表(固定字段:子节点
路径 | 状态 | 最后更新),子节点状态在父节点处的记录只能来自这张表,不能散落
在正文的自由文字里。

- **不是每次子节点状态变化都要级联**,只在子节点进入**终态**时才触发向上
  更新父节点这张表。终态是一个小的枚举集合:`完成` / `否定` / `搁置` /
  `阻塞`。子节点内部的中间进展(比如某个步骤跑完了、某个步骤还在进行中)
  不需要传播到父节点。
- **级联是"把子节点收尾"这个动作本身的最后一步**,不是完成子节点之后另外
  安排的一个任务。谁把子节点推到终态,谁当场就要往上走一级、更新父节点那张
  表;如果这次更新也让父节点跟着跳进了它自己的终态,继续往上一级,直到不再
  跳变为止(这是一个有界的循环,通常走一两级就停)。
- **子节点状态表理论上可以脚本校验**:比对每个子节点自己在 `00-实施计划.md`
  里声明的状态,和父节点表里记录的是否一致,不一致就报警,不依赖人记得住。

## 结论存放的硬性要求

任务进入终态时,在**同一份** `00-实施计划.md` 里追加"结论摘要"一节,以及
一节"产物清单":

- **"结论摘要"必须是实质性结论**——写清楚做了什么、测出/发现了什么、结论
  是什么。不能写成"详见 `99-产物桶`"这种纯指针。产物桶链接是给"想核实细节"
  的读者用的,不是给"只想知道结论"的读者用的。
- **"产物清单"简列 `99-产物桶` 里大致有哪几类东西**(比如"3 个脚本 + 12 次
  调用原始记录 + 1 份对抗审查全文"),不需要复制内容。这样即使 `99-产物桶`
  真的丢失,读者仍然知道"当初做过什么验证、证据本来长什么样子",而不是连
  "有没有验证过"都看不出来。

## 明确排除的问题

本方法论**不**解决"已经写出去的错误结论需要追溯修正"这个问题(比如某个数字
被引用进了多份文档,后来发现算错了,需要挨个找出来改)——那是另一个问题,
靠"改动后 grep 全仓库找引用"这类纪律解决,不是状态级联机制能管的。不要把这
两类问题混在一起处理。

## 从一份需求文档开始:如何搭出初始任务树

拿到一份原始需求/规格文档时:

1. 把这份需求整体当作根任务,建根任务目录(如果还没有的话)和它的
   `00-实施计划.md`
2. 提炼背景(这个任务为什么存在)和目标(要交付什么)
3. 把需求拆成初步的步骤列表——**先全部作为步骤留在根任务的实施计划里**,
   不要一上来就为每个步骤开子任务目录
4. 生成根任务的状态跟踪图
5. 对每个步骤应用上面"什么时候该扇出"的判据,只对真正超阈值/有独立证据链
   需求的步骤执行"扇出操作步骤"
