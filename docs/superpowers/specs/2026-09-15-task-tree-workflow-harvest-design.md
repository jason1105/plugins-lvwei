# task-tree:工作流提炼与复用设计

## 背景

`task-tree` skill(`plugins/task-tree/skills/task-tree/`)定义了一套递归任务分解方法论:每个任务对应一个目录、唯一一份 `00-实施计划.md`、固定的 `01`–`89`/`99` 编号规则、扇出阈值判据、级联终态更新机制。它解决的是"单个任务怎么组织"的问题。

本设计要解决的是下一层问题:**一棵已经完成的任务树,能不能被提炼成一份可复用的工作流模板,供以后同类任务开局时参考,而不是每次都从零想任务分解?**

例子:一个"从需求澄清到验收交付"的软件项目做完之后,它的任务树形状(经历了哪些阶段、哪些阶段会横向扇出、哪些阶段需要纵向深挖)对下一个同类软件项目是有参考价值的;一个调研型任务做完之后,它的形状对下一个调研型任务同样有参考价值。这份参考,应该以一张 mermaid 编排图 + 一段自然语言描述的形式沉淀下来,能被检索、能被复用。

## 需要显式调和的张力

`SKILL.md` 现有规则明确要求:"这个判断是持续性的,不是任务一开始时就要设计出整棵树——先扁平记录,长出规模了再拆分,不要提前设计好一整棵树的结构。"

这条规则的**理由**是:对一个从未做过的任务类型,提前搭结构等于没有依据地瞎猜,猜错了还要拆。但如果已经有一份从真实完成项目里提炼出的模板,"没有依据地瞎猜"这个前提就不成立了——**这是有先例支撑的参考,不是凭空预设**。

因此本设计的立场是:**"别提前设计整棵树"这条规则,管的是"完全没有先例、从零开始"的情况**。一旦存在可复用模板,是否借助它、借助到什么程度,应当是一个用户可以主动做的选择,而不是被这条老规则一刀切禁止。但即便借助了模板,**模板生出的节点依然是普通的、可推翻的节点**,不因为"来自模板"而豁免原有的扇出/深度判据——见下文"一致性规则"。

## 范围

并入现有 `plugins/task-tree/` 插件,不新开插件。新增两块能力:**提炼(harvest)** 和 **复用(reuse)**。

## 能力一:提炼(harvest)

### 触发方式

**根任务**(任务树中唯一没有父任务的顶层任务)的 `00-实施计划.md` 一旦跳进终态(完成/否定/搁置/阻塞),新增一个 PostToolUse hook 自动提示"要不要把这棵树提炼成工作流模板"。

这个 hook 复用 `check-plan-size.sh` 已经端到端验证过的送达机制:exit code 2 + stderr,已确认会作为 "PostToolUse hook blocking error" 送进 Claude 的会话上下文,不是未经验证的假设。

> **留给实现阶段细化的点**:如何从一个 `00-实施计划.md` 的文件路径判定"这是不是根任务"。大致思路是"往上找不到别的 `00-实施计划.md` 就算根",具体判定逻辑(边界条件、性能、跨平台路径处理)交给后续的实现计划阶段处理,本设计不锁死实现细节。

### 提炼内容

用户同意提炼后,由 **Claude 本身**(不是脚本)完成以下工作,不需要额外的解析器或专用工具:

1. 读整棵树:各层 `00-实施计划.md` 的级联子节点状态表 + 状态跟踪图(mermaid)
2. 生成一张**泛化后**的 mermaid 编排图——按真实拓扑(谁扇出了、谁并行推进、谁需要纵向深挖)保留结构,但把节点名从这一次的具体内容("候选A")改写成角色化的、可复用的步骤名("生成候选方案")
3. 写一段**自然语言描述**,说明"这是什么类型的任务"(例如:"软件交付类:从需求澄清到验收上线"),不使用固定的分类标签体系

### 存储

写入 [[ai-memory]] 的 **procedural 层** wiki 页面。不建自定义标签分类表——匹配依赖下文"复用"一节描述的语义检索,不依赖精确标签命中。

## 能力二:复用(reuse)

### 匹配

开新根任务时,由 Claude 主动用这次任务的背景/目标去调用 `memory_query`,按相关度摆出候选模板列表(可能是 0 个、1 个,也可能是多个)。不做"标签精确命中"这种脆弱匹配——ai-memory 自带的 FTS + 语义 + 实体 + 图排序足以处理"相似但描述不完全一致"的情况。

### 决策结构:两层,不是三选一平铺

**第一层:这次要不要用这份模板?**
- 不用 → 根任务的`计划`一节从空白开始,和现有行为完全一致
- 用 → 进入第二层

**第二层(只有选"用"才问):用到多深?**

| 档位 | 行为 | 结构代价 |
|---|---|---|
| **只借阶段清单当起点**(默认档) | 模板的阶段名放进根任务`计划`一节,作为扁平清单草稿 | 零——子目录依然按原有的持续判断纪律,走一步长一步 |
| **裁剪后直接生成目录树**(用户主动选) | Claude 先对比新任务目标与模板来源,提出具体裁剪/调整方案,**用户确认后才建目录** | 有——这是唯一会预先创建真实文件夹结构的档位 |

默认档位选"只借清单"而非平权三选一,理由是:清单只是一段可以随意增删的草稿文字,不构成结构承诺;而生成目录树才是真正有代价、需要用户主动加码信任的动作。二者的差距,比"用不用模板"这第一层决策本身的差距要小得多,不适合和"要不要用"并列成同级选项。

### 一致性规则(必须写进 SKILL.md,不能含糊)

**不管走哪个档位,模板生出的节点依然是可推翻的普通节点。** 该收拢成一个节点、该合并、该删除,一样要按 `SKILL.md` 原有的扇出/深度判据持续判断,不因为"这是从模板来的"而享有免检特权。

这条规则存在的理由:如果模板生成的结构被默认当作"已经验证过、不用再审视",就相当于给"提前设计"开了一个后门——用"这是复用来的"当借口,绕开了任务树方法论本来要求的持续判断纪律。模板的价值是**减少从零构思的成本**,不是**免除持续判断的责任**。

## 质量反馈

不自建版本号或使用次数统计。复用后如果发现某个模板不好用、过时,直接调用 ai-memory 的 `memory_feedback`(`not_helpful` / `stale`),交给它自身的衰减/留存机制处理,不重复造轮子。

## 降级行为

新增的 hook 是一段独立运行的 shell 脚本,无法感知当前会话有没有配置 ai-memory MCP server——所以它**总会**在根任务终态跳变时发出提示,这一步不做任何前置判断,保持和 `check-plan-size.sh` 一样的"纯机械检测、无环境感知"风格。

真正的降级发生在**下一步**,即 Claude 响应提示、准备调用 `memory_write_page`/`memory_query` 的时候:如果当前会话的工具列表里没有 ai-memory 相关工具,Claude 直接告知用户"未配置 ai-memory,跳过这项能力"并停止,不报错、不重试、不阻塞原有的 task-tree 核心流程。复用侧(开新任务时的模板检索)同理——没有 `memory_query` 可调用,就直接跳过检索,当作没有可用模板处理。

## 涉及文件(实现阶段的落点,本设计不做实际改动)

| 文件 | 改动性质 |
|---|---|
| `plugins/task-tree/skills/task-tree/SKILL.md` | 新增两节:提炼流程(含一致性规则)、复用流程(含两层决策结构) |
| `plugins/task-tree/skills/task-tree/reference.md` | 补一段"为什么模板节点不能免检"的推导过程与反例,延续现有的"为什么 X"分节风格 |
| `plugins/task-tree/hooks/hooks.json` + 新脚本 | 新增一个 PostToolUse hook,检测根任务终态跳变,复用 `check-plan-size.sh` 已验证的 exit-2/stderr 送达机制 |

## 测试思路(供后续实现计划参考)

沿用 `check-plan-size.sh` 已经在用的"构造 `00-实施计划.md` + 端到端跑 hook,拿真实 exit code 验证"方法,新增覆盖:

- 根任务终态跳变时,新 hook 是否正确触发提示
- 非根任务终态跳变时,新 hook 是否正确保持静默
- mermaid 编排图的泛化质量(人工抽查,非机械可断言)
- ai-memory 不可用时,提炼与匹配两条路径是否都能优雅跳过而不报错
